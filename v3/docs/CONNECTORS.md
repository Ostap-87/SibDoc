# Коннекторы, выписки банков и уведомления

Коннектор забирает данные из внешней системы и кладёт их в слоты (`wide_table`,
`purchase`, `ru_dt`, `cn_dec`, `bank`, `contract_register`, …). Уведомления отправляют итоги
прогона и ошибки коннекторов в рабочие чаты. Всё настраивается в `config/system.yaml`
(блоки `connectors:` и `notifications:`) и **по умолчанию выключено** (`enabled: false`).

## Статус коннекторов

Каждый коннектор сообщает один из трёх статусов (`GET /api/connectors` → поля `status`,
`status_title`, `need`, `need_from`, `verified`, `exports`; `GET /api/connectors/catalog` →
`capability`). Те же сведения — в таблице «Статус коннекторов РФ–Китай» на странице коннекторов.

| Статус | Когда |
|---|---|
| `works` — «работает» | обмен реализован и параметры доступа заполнены |
| `via_exports` — «работает через выгрузки» | прямого доступа нет, задана папка выгрузок `export_dir` |
| `needs_access` — «нужен доступ: что именно — у кого» | ни того, ни другого; `need` и `need_from` говорят, что получить и у кого |

`verified`: `real` — проверено на реальном протоколе; `emulator` — **проверено на эмуляторе, на
реальной системе — после выдачи доступа**; `none` — прямого обмена нет, только выгрузки.

| Система | Тип | Что работает сейчас | Проверка | Что нужно для прямого доступа — у кого |
|---|---|---|---|---|
| Почта брокеров | `imap` | вложения Excel / CSV / XML / PDF / ZIP | реальный протокол | адрес IMAP, ящик, пароль приложения — администратор почты |
| Папка на сервере | `folder` | файлы брокеров, выгрузки FineBI | реальный протокол | папка с правом чтения — администратор сервера |
| SFTP | `sftp` | то же по SFTP, проверка ключа сервера | реальный протокол | учётная запись с ключом, отпечаток ключа сервера — брокер / администратор SFTP |
| REST/JSON API | `rest` | записи → CSV в слот | реальный протокол | адрес, вход, токен — владелец API |
| БД (FineBI и др.) | `database` | SQL-запрос на слот | реальный протокол | строка подключения с пользователем на чтение — администратор БД |
| SAP S/4HANA | `sap_odata` | OData v2 / v4 | реальный протокол | OData-сервис, пользователь или OAuth-клиент — Basis |
| **1С** | `onec_odata` | OData; **выгрузки EnterpriseData** и `kl_to_1c.txt` из папки | эмулятор | публикация базы с «стандартным интерфейсом OData», объекты в составе, пользователь — администратор 1С |
| **Kingdee 金蝶云星空** | `kingdee` | WebAPI: вход, ExecuteBillQuery, страницы, повторный вход | эмулятор | адрес K3Cloud, 账套ID, пользователь WebAPI или AppID/AppSecret — администратор Kingdee китайской стороны |
| **Yonyou 用友 YonBIP** | `yonyou` | OpenAPI: токен, адрес дата-центра, страницы, обновление токена | эмулятор | 自建应用 (AppKey/AppSecret), адреса шлюза или tenant_id, путь API — администратор YonBIP |
| **Банк** | `bank_fx_control` | **выписки** 1С «Клиент-банк», camt.053, MT940, CSV/Excel банков КНР | разбор форматов — тесты на образцах | API банка (ВБК, УНК): договор, client_id/secret, сертификат — банк |
| **Единое окно КНР 单一窗口** | `cn_single_window` | **выгрузки** XML 报关单 DecMessage, Excel-список 报关单, файлы брокера | разбор форматов — тесты на образцах | открытого API нет; UKey (卡介质) и API ПО брокера — импортёр / брокер |
| **ЭТРАН (РЖД)** | `etran` | **выгрузки** из АРМ ЭТРАН в папку (слот транспортных документов) | — | договор с ОАО «РЖД», пользователь, ЭЦП, веб-сервис — см. ниже |

Эмуляторы — `tests/emulators.py` (настоящий HTTP на 127.0.0.1, стандартная библиотека Python):
`python3 tests/emulators.py kingdee 8765` поднимает эмулятор, на который можно направить
коннектор из интерфейса. Тесты: `tests/test_bank_connectors.py`.

## Выписки банков → проверка «8. Оплаты»

Выписки, которые бухгалтер уже получает, загружаются в слот **«Банк: выписки»** (вручную, из
папки коннектора `bank_fx_control` или из папки 1С). Формат определяется по содержимому
(`app/services/bank_statements.py`), имя файла не важно:

| Формат | Где взять | Как читается |
|---|---|---|
| **1CClientBankExchange** (`kl_to_1c.txt`) | «Клиент-банк» / интернет-банк → «Экспорт в 1С»; 1С:ДиректБанк | Windows-1251 или DOS (cp866, по строке `Кодировка=`); `СекцияРасчСчет … КонецРасчСчет`, `СекцияДокумент=<вид> … КонецДокумента`. Поступление — наш счёт в `ПолучательСчет` (или `ДатаПоступило`), списание — в `ПлательщикСчет` (`ДатаСписано`). Контрагент — `Плательщик1`/`Получатель1` (или `Плательщик` без «ИНН …»), назначение — `НазначениеПлатежа`. **Валюты в формате нет** — она берётся из номера счёта (цифры 6–8: 810 — рубли, 840 — доллары, 156 — юани). Версии 1.01–1.03 |
| **ISO 20022 camt.053** (также camt.052, camt.054) | интернет-банк, SWIFT, банки КНР и РФ | `BkToCstmrStmt/Stmt/Ntry` (а также `Rpt`, `Ntfctn`); строка = `NtryDtls/TxDtls` (пакетная проводка — по строке на каждую). Сумма и валюта — `Amt@Ccy`, направление — `CdtDbtInd` (CRDT — поступление), сторно — `RvslInd`, статус — `Sts` (`BOOK`/`PDNG`; версии 02 и 08+). Контрагент: для CRDT — `RltdPties/Dbtr` (`Nm` или `Pty/Nm`), для DBIT — `Cdtr`; назначение — `RmtInf/Ustrd` + номера из `Strd`; референс — `EndToEndId`, иначе `AcctSvcrRef` |
| **SWIFT MT940** (`*.sta`, `*.940`, `*.mt940`, `*.txt`) | интернет-банк, SWIFT | выписка начинается с `:20:`, счёт `:25:`, валюта — из `:60F:`/`:60M:`, проводка `:61:` (дата, `C`/`D`/`RC`/`RD`, сумма с запятой, код операции, референсы) и следующее за ней `:86:` |
| **CSV / Excel банков КНР** | 网上银行 → 账户明细 / 交易明细 → 导出 | «шапка» с реквизитами над таблицей пропускается (`账号：…` берётся как наш счёт), колонки — по словарю полей: 交易日期, 借方发生额 / 贷方发生额, 交易金额 (со знаком), 借贷标志 / 收支方向, 币种 / 交易货币, 对方户名, 对方账号, 对方开户行, 摘要 / 用途 / 附言 (склеиваются), 交易流水号; выписки с колонками 付款人 / 收款人 — контрагент та сторона, чей счёт не наш |
| **CSV / Excel банков РФ** | интернет-банк | «Дата операции», «Дебет» / «Кредит», «Контрагент» / «Плательщик» / «Получатель», «Назначение платежа» |

Неточности, о которых надо знать:
* у MT940 поле `:86:` в стандарте свободное; разобраны подполя `?20…?29`, `?32/?33`, `?31`
  (немецкая структура) и ключи `/NAME/`, `/ORDP//NAME/`, `/BENM//NAME/`, `/REMI/`; у других
  банков контрагент может остаться пустым (назначение берётся целиком) — сверить на реальной выписке;
* заголовки CSV/Excel банков КНР — по типичным выгрузкам (工商银行, 建设银行, 招商银行, 中国银行),
  официального описания нет; новый заголовок — синоним в `config/fields.yaml` (блок «выписки банков»);
* `1CClientBankExchange` — формат рублёвых платёжных поручений; выписки валютных счетов банки
  выгружают в нём не всегда — для них лучше camt.053 или MT940;
* ведомость банковского контроля (ВБК) и справки о подтверждающих документах пока не разбираются.

Проверка **«8. Оплаты»** (`config/rules/payments.yaml`) — две группы строк:
* **платёж**: контракт по номеру в назначении платежа (кириллица и латиница сравниваются
  одинаково: `ДЕМО.1001-01А` = `DEMO.1001-01A`, `СХ` = `CX`), по номеру инвойса (если загружен
  слот инвойсов), по УНК, по основному номеру контракта (REVIEW); плательщик/получатель против
  сторон контракта (ДТ, 报关单, реестр договоров, SAP/1С) — нечётко, с транслитом и без «ООО / LLC /
  CO., LTD. / 有限公司», порог и синонимы — в правилах; валюта (пересчёт по курсу ЦБ РФ или НБК на
  дату платежа — REVIEW); дубли; код вида валютной операции `{VO…}` выводится отдельной колонкой;
  платёж без контракта — ISSUE (поступление) / REVIEW (списание);
* **контракт**: сумма оплат против ожидаемой (инвойсы → реестр договоров → ДТ РФ → 报关单 →
  SAP/1С, первый источник, где сумма есть): полностью (допуск `amount_tolerance_pct` /
  `amount_tolerance_abs` — комиссии банков-корреспондентов) — OK; частично — REVIEW; переплата —
  ISSUE (после пересчёта валют — REVIEW: может быть разница курсов); оплат нет — REVIEW.
Пояснения — по-русски (`detail`) и по-китайски (`detail_zh`). Демо: `python3 tools/make_demo_bank.py`,
`data/demo/bank/` (8 платежей, все случаи), `verify.sh` сверяет итог вместе с инвойсами пакета ВЭД: 14 строк, 5 OK, 2 ISSUE, 7 REVIEW (без инвойсов — 6 OK,
1 ISSUE, 7 REVIEW; вторая ISSUE — переплата ДЕМО.1002-02А против инвойса INV-DEMO-2604).

## 1С

**OData** (`onec_odata`): `GET <base_url>/odata/standard.odata/<Объект>?$format=json`, basic-вход
(логин и пароль по-русски передаются в UTF-8), страницы `$top`/`$skip`, `$filter`, `$select`,
ошибки `{"odata.error": …}` показываются текстом 1С. Что попросить у администратора 1С:
1. опубликовать базу на веб-сервере (Конфигуратор → Администрирование → Публикация на веб-сервере)
   с флажком «Публиковать стандартный интерфейс OData»;
2. включить нужные объекты в состав OData (обработка «Настройка стандартного интерфейса OData»);
3. завести пользователя 1С с правом чтения этих объектов.
*Проверено на эмуляторе (список объектов, страницы, фильтр, неверный пароль, неизвестный объект);
на реальной базе — после выдачи доступа.*

**EnterpriseData** (без OData — папка `export_dir` у коннектора 1С или загрузка файла в слот):
файл обмена `Message / msg:Header / Body` («Синхронизация данных через универсальный формат»,
обмен через каталог). Разбираются (`config/enterprise_data.yaml`, пути к свойствам можно дописать
без кода):

| Объект | Слот | Что берётся |
|---|---|---|
| `Документ.ПоступлениеТоваровУслуг` | `purchase` | дата, номер, контрагент, договор, валюта, строки товаров: номенклатура (артикул), количество, цена, сумма, номер ГТД; кг/т → вес нетто в т и цена за т. Контейнеров в 1С нет — эти строки участвуют в «Оплатах», но не в сверке цен по контейнерам |
| `Документ.ГТДИмпорт` | `ru_dt` | номер ГТД, дата, контрагент (отправитель), договор, валюта, товары: код ТН ВЭД, таможенная и фактурная стоимость, страна |
| `Справочник.Договоры` | `contract_register` (новый слот) | номер (или из наименования «Контракт № … от …»), дата, вид, контрагент, валюта взаиморасчётов, сумма |
| `Справочник.Контрагенты` | — | наименование и ИНН для ссылок, выгруженных только идентификатором |

Один файл даёт данные нескольким слотам: при загрузке в слот берётся его часть, мост папки
отдаёт файл во все подходящие слоты. *Имена свойств в разных версиях формата (1.6 … 1.20)
немного различаются — пути заданы с запасными вариантами; проверено на вымышленном файле
версии 1.8, на реальной выгрузке — сверить и при необходимости дописать путь в YAML.*

## Kingdee K3Cloud 金蝶云星空

WebAPI: вход `AuthService.ValidateUser` (`acctID`, `username`, `password`, `lcid`) или
`AuthService.LoginByAppSecret` (`auth_mode: app_secret`, `app_id`, `app_secret_env`); сессия —
cookie `kdservice-sessionid` (и одноимённый заголовок); запрос
`DynamicFormService.ExecuteBillQuery` с телом `{"data": {FormId, FieldKeys, FilterString,
OrderString, TopRowCount, StartRow, Limit}}` (старый клиент — `{"parameters": [...]}`,
`body_style: parameters`); ответ — массив строк в порядке FieldKeys; страницы — `StartRow`/`Limit`.
Ошибка — `Result.ResponseStatus` с `IsSuccess: false`, `Errors[].Message`, `MsgCode`; при потере
сессии (`MsgCode: 1`, «会话信息已丢失») коннектор входит заново и повторяет страницу.
Что попросить у администратора Kingdee: адрес K3Cloud, ID набора данных (账套ID), пользователя с
правом WebAPI на объект (или AppID/AppSecret интеграции «第三方系统登录授权»), FormId и FieldKeys.
*Проверено на эмуляторе (страницы, вход по паролю и приложением, неверный пароль, истечение
сессии, ошибка поля, старый формат тела); на реальной системе — после выдачи доступа.*
Не реализован вход по подписи (`X-Api-Signature`, новые SDK); тексты `MsgCode` и предел `Limit`
(по опыту — до ~2000 строк за запрос) — уточнить на реальной системе.

## Yonyou YonBIP 用友

OpenAPI самостоятельного приложения (自建应用): адреса дата-центра — `auth_url` и `gateway_url`
или `tenant_id` (`GET …/open-auth/dataCenter/getGatewayAddress?tenantId=` — *путь сервиса
дата-центров по открытым описаниям не подтверждён, задаётся `discovery_url`*); токен —
`GET <auth_url>/open-auth/selfAppAuth/getAccessToken?appKey&timestamp&signature`, подпись
`Base64(HmacSHA256(AppSecret, "appKey"+AppKey+"timestamp"+мс))` (в новых версиях путь
`…/selfAppAuth/base/v1/getAccessToken` — параметр `token_path`); запрос —
`<gateway_url>/<api_path>?access_token=…`, тело `{"pageIndex", "pageSize", …}`, записи
`data.recordList`, конец — по `pageCount`/`recordCount` или короткой странице. Токен обновляется
по сроку `expire` (с запасом `token_margin_sec`) и когда API ответил «токен недействителен»
(HTTP 401, код из `token_error_codes` или текст «token 过期/失效/invalid»).
Что попросить у администратора YonBIP: создать 自建应用 в 开放平台, выдать AppKey/AppSecret с правом
на API нужного документа, сообщить дата-центр (или tenant_id) и путь API (закупка, приход …).
*Проверено на эмуляторе (дата-центр, подпись, страницы, неверный AppSecret, ошибка API, истечение
токена обоими способами); на реальной системе — после выдачи доступа. Коды ошибок «токен
истёк» у реальной системы — уточнить и дописать в `token_error_codes`.*

## Единое окно КНР 单一窗口

Открытого API для третьих лиц нет: работа в 单一窗口 и клиенте 中国电子口岸 идёт под ключом-носителем
UKey (卡介质 / IC-карта) импортёра или таможенного брокера. Поэтому основной режим — **папка
выгрузок** `export_dir`, файлы распознаются по содержимому (имя может быть любым):

| Что сохраняет сотрудник / брокер | Слот |
|---|---|
| XML-сообщения 报关单 `DecMessage` (DecHead / DecList / DecContainers) — «导出报文» в 单一窗口 / ПО брокера | `cn_dec` целиком (товары, контейнеры) |
| Excel-список 报关单: 货物申报 → 数据查询/统计 → 报关数据查询 → 导出 (统一编号, 海关编号, 申报日期, 境内收发货人, 境外发货人, 合同协议号, 申报地海关, 报关单状态 …) | `cn_dec` (шапки деклараций) |
| Excel/CSV брокера с товарами 报关单 (海关编号, 商品编号, 单价, 净重 …) | `cn_dec` |
| PDF-распечатки 报关单 | блок «Сканы деклараций» (OCR) |

*Структура Excel-выгрузки «报关数据查询» официально не опубликована — колонки распознаются словарём
полей; квитанции (回执) не разбираются.* Таблицы SAP/FineBI (wide table, Purchase) мост не
принимает за 报关单. Для прямого обмена нужно: у брокера — есть ли у его ПО (报关软件) API и
доступ к нему; у импортёра — UKey и учётная запись 单一窗口.

## ЭТРАН (РЖД)

Остаётся `needs_access`. Что именно нужно и у кого:
1. **договор с ОАО «РЖД» на электронный обмен перевозочными документами в АС ЭТРАН** —
   заключает грузоотправитель/грузополучатель (или его ж/д экспедитор) через **ТЦФТО** (центр
   фирменного транспортного обслуживания) своей дороги;
2. **пользователь ЭТРАН** (логин, пароль) с правами на нужные документы и **код организации /
   плательщика**;
3. **квалифицированная электронная подпись организации** (ГОСТ, КриптоПро CSP) на сервере SibDoc —
   документы и запросы в ЭТРАН подписываются; выдаёт удостоверяющий центр;
4. для обмена «система — система» — **адрес веб-сервиса ЭТРАН и его руководство программиста**
   (описание XML-запросов: накладные, состояние вагонов/контейнеров) — выдаёт РЖД по договору,
   в открытом доступе его нет; поэтому формат запросов в SibDoc не реализован.
Заявку обычно подаёт отдел логистики или ж/д экспедитор. Пока доступа нет — **папка выгрузок**:
журнал накладных из АРМ ЭТРАН «в Excel» / CSV или файлы экспедитора; файлы с колонками «Номер
накладной», «Номер вагона», «Станция отправления» … распознаются по содержимому и идут в слот
транспортных документов пакета ВЭД `transport` (параметр `slot` — если нужен другой слот; накладные
проверяются в «7. Пакет документов»). *Названия колонок выгрузки зависят от версии АРМ — сверить
на реальном файле.*

## Как включить, когда появится доступ

1. Кнопка «Проверить» отвечает «Задел: нужен доступ — …» и называет, что и у кого получить;
   статус коннектора — в таблице «Статус коннекторов РФ–Китай».
2. Когда доступ выдан: заполните поля коннектора в `config/system.yaml`, укажите **имена
   переменных** с паролями (ниже) и нажмите «Проверить». Ответ «доступ есть» — ставьте
   `enabled: true` и перезапустите сервис.
3. Пока прямого доступа нет, у 1С, ЭТРАН, Единого окна и банка укажите `export_dir` — папку, куда
   сохраняются выгрузки; статус станет «работает через выгрузки». Файлы 报关单 от брокера можно
   забирать и почтой или по SFTP.

## Пароли и ключи

В YAML пароли **не пишутся**. Пишется имя переменной окружения:
`password_env: SIBDOC_IMAP_PASSWORD`, `key_env: SIBDOC_WECOM_KEY` (или `${ИМЯ}` внутри строки).
Значения задаются на сервере: файл `.env` рядом с `docker-compose.yml` (в git не попадает),
секреты Docker или переменные службы. Если пароль всё же записан в YAML, интерфейс покажет
предупреждение, но значение не выдаст ни в интерфейс, ни в журнал (токены Yonyou и сессии
Kingdee тоже вычищаются из текстов ошибок).

Для SFTP сначала добавьте ключ сервера: `ssh-keyscan -p 22 host >> known_hosts` (отпечаток
сверьте с администратором) или укажите `host_key_sha256`. Опция `insecure_accept_new_host: true`
— только для первой настройки.

## В какой слот попадает файл

По `slot_rules` (регулярное выражение по имени файла, для почты — ещё и по отправителю) или
по началу имени файла (`slots`); у мостов `export_dir` — ещё и по содержимому
(`detect_content: true`, `app/connectors/sniff.py`). Примеры правил по умолчанию:
`报关单|customs.?dec|cn_dec` → `cn_dec`; `ДТ|ESADout|gtd|ru_dt` → `ru_dt`. Уже забранные письма и
вложения хранятся в `storage/connectors/<id>.seen.json` — чтобы перечитать всё заново, удалите
этот файл.

Каждая проверка, забор данных, ошибка коннектора и отправка уведомления записываются
в журнал без секретов.
