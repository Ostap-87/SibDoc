# Руководство специалиста пост-контроля

Этот документ — для тех, кто ежемесячно делает пост-контроль деклараций.
Никакого программирования не требуется: загрузка — через веб-интерфейс,
параметры — через экран «Параметры проверок» или файлы `config/rules/*.yaml`.

---

## 1. Рабочий цикл (3 шага)

```
Шаг 1. Загрузить файлы в слоты
Шаг 2. (при необходимости) подправить параметры проверок
Шаг 3. Нажать «Запустить проверку» → скачать Excel и/или PDF
```

Каждый прогон делает две вещи:

1. **Data-quality детекцию** — проверяет сами данные ДО сверки: где чего не хватает,
   какая колонка пустая, где текст вместо числа, где дубли.
2. **6 проверок** по хендбуку «Post Control Report Handbook» (июнь 2026).

---

## 2. Источники данных и их связи

| Слот | Что это | Откуда берётся | Обязательный |
|---|---|---|---|
| `wide_table` | Данные по декларациям (CD) | FineBI «Widetable» | **да** |
| `purchase` | Данные SAP по закупкам | FineBI «Purchase» | **да** |
| `sap_vs_cd` | Ручная сводная таблица «SAP vs CD» | ваша рабочая книга | нет |
| `cd_drafts` | Черновики деклараций | выгрузка от брокера | нет |
| `hs_reference` | Утверждённая таблица грейд/завод/HS-код | встроенная, 84 строки | нет (есть builtin) |
| `cde_reference` | Справочник элементов декларации | встроенная, 100 строк | нет (есть builtin) |

**Как связаны между собой:**

```
wide_table ──container_num──► purchase          (цены, контракты)
wide_table ──decl_num───────► sap_vs_cd         (полнота)
wide_table ──product_code───► hs_reference      (HS-коды)
cd_drafts ──заявл. модель───► cde_reference     (элементы декларации)
```

Если связующая колонка пустая или отсутствует — DQ-детекция покажет это
**до** проверок, с указанием, какая проверка пострадает.

### Обязательные колонки

**wide_table:** `decl_num, container_num, contract, incoterms,
shipreport_incoterms, extra_costs_value, product_code, product_name, material,
products_price, products_net_weight, storage_location, decl_issue_status`

**purchase:** `Container number, Price, Main contract, Add contract, Net weight`

Отсутствие обязательной колонки = красная строка в блоке DATA_QUALITY
с указанием секции и пострадавшей проверки.

## 3. Проверки и их правила

### 0. Completeness (полнота) — хендбук, шаг 1.3
Каждая CD должна быть **в обеих** таблицах: wide table и ручной «SAP vs CD».
Проверка в обе стороны: что есть в wide, но нет в ручной, и наоборот.

Файл правил: `config/rules/completeness.yaml`

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `direction` | `both` | направление сверки |
| `max_listed` | `50` | сколько номеров CD выводить в отчёт |

### 1. Price (цены) — хендбук, часть I
Цена CD против цены SAP **по каждому контейнеру**.

- CD часто декларирует цену **за кг** (9.661), SAP хранит **за тонну** (9661) —
  значения ниже `per_kg_threshold` автоматически умножаются на 1000.
- Контейнер может встречаться в Purchase несколько раз: совпадение
  **с любой строкой** = OK («фейковый no», повторный контейнер, п. 2.3.1).
- Контракты схемы **BP SEA** исключаются (проверка раз в 6 месяцев).
- При расхождении в отчёт пишется адрес эскалации.

Файл правил: `config/rules/price.yaml`

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `tolerance_abs` | `0.01` | допустимое расхождение цены |
| `per_kg_threshold` | `100` | ниже — считаем «за кг», ×1000 |
| `bp_sea_contract_patterns` | `[]` | подстроки контрактов BP SEA для исключения |
| `escalation` | `SISH finance / export teams / CN OL / SVS team` | куда эскалировать |

**Пример:** чтобы исключить контракты BP SEA, добавьте паттерны:
`bp_sea_contract_patterns: ["BP-SEA", "SEA."]`

### 2. HS code — хендбук, часть II
Код ТН ВЭД из CD против утверждённой таблицы грейд/завод/код.

Три уровня результата:
- **OK** — точное совпадение;
- **REVIEW** — то же семейство (первые 6 знаков), другой суффикс —
  проверить дополнения 2026 года / маппинг грейдов;
- **ISSUE** — код отсутствует в утверждённой таблице.

Файл правил: `config/rules/hs_code.yaml`

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `family_prefix_len` | `6` | длина префикса «семейства» для REVIEW |

Справочник обновляется заменой файла `references/hs_codes.csv`
(колонка `hs_code`) или загрузкой своего файла в слот.

### 3. Incoterms — хендбук, часть III
Инкотермс CD против инкотермса из shipreport (SAP).

**Исключение Qingdao/BZA (п. 3.2.1):** если склад совпадает с ключевыми словами,
CD = CIF, SAP = C&F и заполнен `extra_costs_value` — строка квалифицирована (OK).

Файл правил: `config/rules/incoterms.yaml`

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `qingdao_keywords` | `["青岛", "qingdao"]` | как распознать склад-исключение |
| `qingdao_allowed.cd / .sap` | `CIF / C&F` | разрешённая пара для исключения |

### 4. Decl. elements (элементы декларации)
Заявленная модель в черновике CD против мастер-данных SAP (справочник CDE).

Файл правил: `config/rules/decl_elements.yaml`

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `model_column_patterns` | `["型号", "model"]` | как найти колонку модели в черновике |

### 5. Contract (контракты)
Контракт CD против SAP `Main contract` + `Add contract` по контейнеру.
Сравнение «умное»: игнорируются пробелы и дефисы, регистр не важен;
контракт в wide table может быть склеенным, а в Purchase — отдельными строками.

Файл правил: `config/rules/contracts.yaml`

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `ignore_chars` | ` \-–—` | символы, игнорируемые при сравнении |

---

## 4. Статусы строк

| Статус | Значение | Что делать |
|---|---|---|
| **OK** | всё совпало | ничего |
| **ISSUE** | расхождение | разбирать, при ценах — эскалация по адресу из отчёта |
| **REVIEW** | недостаточно данных для однозначного вывода | проверить вручную |
| **SKIPPED** | проверка неприменима (BP SEA, нет источника) | ничего |

---

## 5. Как читать блок DATA_QUALITY

Каждая строка отвечает на вопрос «где и что не так с данными»:

| Поле | Пример | Смысл |
|---|---|---|
| severity | `ERROR` / `WARNING` / `INFO` | критичность |
| source | `wide_table` | в каком источнике |
| section | `sap_link` | в какой секции/блоке данных |
| column | `extra_costs_value` | в какой колонке |
| issue | «Колонка пустая (0% из 55)» | что не так |
| affected_rows | `55` | сколько строк затронуто |
| examples | конкретные значения | примеры мусора/дублей |
| impact | «пострадают проверки: 3. Incoterms» | на что влияет |

**Типовые находки:**

- `ERROR · колонка отсутствует` — выгрузка неполная или изменилась структура FineBI;
  перепроверьте фильтры выгрузки.
- `ERROR · колонка пустая` — например, `extra_costs_value` не заполнен: исключение
  Qingdao/BZA не сработает, расхождения CIF/C&F упадут в ISSUE.
- `WARNING · нечисловые значения` — в цене текст/мусор: цена строки не сверится.
- `WARNING · дубли ключа в wide_table` — возможно, задвоенная выгрузка.
- `INFO · дубли контейнера в purchase` — нормально, обрабатывается правилом 2.3.1.

## 6. Добавление и изменение параметров (вариативность)

**Что можно менять самостоятельно:**
- любые значения в `config/rules/*.yaml` — через веб-интерфейс
  (шаг 2 «Параметры проверок») или правкой файла на сервере; применяется
  **сразу, без перезапуска**;
- справочники HS-кодов и элементов декларации — заменой файлов в `references/`
  или загрузкой своих;
- включение/выключение проверок — `config/system.yaml`, блок `checks`
  (`enabled: true/false`; после правки файла — перезапуск контейнера).

**Что требует разработчика (см. AGENT_GUIDE):**
- новая проверка (новый плагин в `app/checks/`);
- новая секция данных или новое DQ-правило.

## 7. Отчёты

**Excel** (`post_control_report.xlsx`): листы `SUMMARY`, `SOURCES`,
`DATA_QUALITY` и по листу на проверку; статусы раскрашены
(зелёный OK / красный ISSUE / жёлтый REVIEW / серый SKIPPED).

**PDF** (`post_control_report.pdf`): сводка, источники, все DQ-находки
и отклонения (ISSUE/REVIEW) по каждой проверке — формат «на подпись».

Оба файла лежат в `storage/reports/` на сервере и скачиваются из интерфейса.

## 8. Сканированные декларации (OCR) и предпросмотр

Блок **«Сканированные декларации (OCR)»** (шаг 1.5 в интерфейсе):

1. Загрузите сканы — PDF/JPG/PNG/TIFF/BMP, **можно сразу несколько файлов**
   (массовая загрузка; каждый файл обрабатывается независимо, ошибка в одном
   не прерывает остальные).
2. Нажмите **«Распознать»** — система читает текст на **русском, английском
   и китайском** одновременно и извлекает из секций документа: номер декларации,
   контейнер, контракт, инкотермс, код ТН ВЭД, цену за единицу, вес нетто,
   заявленную модель.
3. Каждое поле получает статус: **found** (зелёный) — извлечено и валидно;
   **review** (жёлтый) — извлечено, но выглядит сомнительно (проверьте глазами:
   OCR мог перепутать буквы, например кириллическую «С» и латинскую «X» в
   контрактах «СХ.»); **missing** (красный) — не найдено в документе.
4. Блок **«Предварительная проверка»** показывает таблицу — как данные лягут
   в Excel: файл × извлечённые параметры с раскраской по статусу.
5. Кнопка **«Excel предпросмотра»** скачивает `scan_preview.xlsx` — значения
   расставлены в нужные ячейки (маппинг поле → колонка задаётся в
   `config/scan_mapping.yaml`, меняется без кода), ячейки раскрашены
   по статусу извлечения.

**Настройка под ваши бланки:** паттерны извлечения — в `config/scan_fields.yaml`
(регулярные выражения RU/EN/ZH, первое совпадение побеждает). Добавить паттерн
под новый формат бланка можно самостоятельно, без разработчика.

**Совет по качеству:** сканы от 200 DPI и выше распознаются заметно лучше;
многостраничные PDF обрабатываются постранично.

## 9. Мультиязычность интерфейса

В шапке — переключатель **RU / EN / 中文**: весь интерфейс (шаги, кнопки,
таблицы, блоки результатов и предпросмотра сканов) мгновенно переводится.
Выбор запоминается в браузере сотрудника. Проверки и отчёты при этом
не зависят от языка интерфейса.
